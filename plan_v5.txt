# Plan v5: Migrate xlgen_v2 to xlgen_v3

## Context

xlgen_v2 is a 4-stage Excel-to-structural-table pipeline (xl_init -> xl_parse -> xl_image -> xl_kg). xlgen_v3 is a clean monorepo refactor that renames xl_kg -> xl_table, centralizes output paths, separates Streamlit UI from business logic, and standardizes stage entry points. The spec lives in `xlgen_v3/Claude Code Prompt — Build xlgen_v3 from.ini`.

xlgen_v3 contains the migrated monorepo implementation (see repo root). xlgen_v2 must NOT be modified.

### 0.4 Two-file configuration layout (YAML) + `core/config.py`

**Requirement:** After xlgen_v3 exists, all tunable pipeline settings MUST be sourced from exactly **two** YAML files under `config/` (plus the Python loader below — not a third “config file” in the sense of editable knobs):

| File | Contents |
|------|----------|
| `config/stages.yaml` | Nested sections: `xl_init`, `xl_parse`, `xl_table`, `xl_image`. Defaults are migrated from: `xl_init/config.py` (dataclass fields), `xl_parse/parse_tools/models.py` (`Config`), former xl_kg `config_default.yaml` → `xl_table`, and `xl_image/config.py` / image tunables → `xl_image`. Single place on disk for stage-specific parameters. |
| `config/general.yaml` | Cross-cutting / orchestrator settings: default logging level, run-id naming hints, optional feature flags that are not owned by one stage alone, orchestrator/Streamlit defaults (e.g. default paths shown in UI), and any other global options. |

`core/config.py` loads **both** YAML files (general merged with stage tree), validates, and exposes a `PipelineConfig` (or equivalent) with sub-configs per stage plus `general`. Stage packages may keep thin typed wrappers that read from the merged structure (no duplicate competing defaults outside these two files).

**Streamlit (Phase 6):** The orchestrator app MUST let the user **view and change** overrides for **`xl_parse`** and **`xl_table`** (sidebar widgets and/or YAML `st.text_area` that merges with loaded defaults — same effective knobs as `stages.yaml`). The user MUST also be able to view and change **`general.yaml`**-backed options in the UI (a “General” section). Saving: write-through to the two YAML files **or** session-only overrides applied for the next run (implementation choice; document which in README).

## Phase 6: Streamlit Orchestrator

Create `apps/orchestrator/app.py` with structure **aligned to** `xlgen_v2/xl_kg/main.py` (same structural patterns, adapted for multi-stage):

**Structural parity with xl_kg `main.py`:**
- `st.set_page_config`, title, **sidebar** for inputs and config overrides
- **`concurrent.futures.ThreadPoolExecutor` (max_workers=1)** + **Future** stored in `st.session_state`; poll with `future.done()`, `time.sleep(1)` + `st.rerun()` while running (no double-submit, no unsafe concurrent mutation)
- Clear **session state** keys per stage or per long-running operation (e.g. `init_future`, `parse_future`, …)
- **Tabs** for summary / explorer / logs where applicable (mirror xl_kg’s tab pattern for xl_table results; other stages borrow from their v2 `main.py` flows)
- **No business logic in the UI** — only calls public entry points and renders artifacts

**Imports:** only public entry points (`run_init`, `run_parse`, `run_table`, `run_image`); **`core.paths`** for output routing; **`core.config`** for merged two-file YAML (0.4).

**Config in UI (mandatory):** User can **click and change** effective settings for **`xl_parse`** and **`xl_table`** (and **`general`** from `config/general.yaml`). Prefer the same pattern as xl_kg’s `_build_config_from_ui` (load defaults from `core.config`, patch from widgets). Optionally expose raw YAML fragments for power users.

**Execution: CLI / pipe vs in-app (xl_init → xl_parse focus):**
- **Documented CLI (pipe-friendly):** In-sidebar or help panel, show exact commands equivalent to in-app runs, e.g.  
  `python scripts/run_init.py --input <xlsx> --run-id <id>`  
  then  
  `python scripts/run_parse.py --init-dir <dir> --run-id <id>`  
  so users can run the same steps in a terminal or shell pipeline.
- **In-app buttons:** **“Run xl_init”** and **“Run xl_parse”** (sequential workflow: parse consumes init output paths from `core.paths`), calling the same functions/scripts use internally. Optional: **“Run full pipeline”** chaining all stages (may reuse Phase 5 `run_pipeline.py` logic).

Reference material from:
- `xl_init/main.py`: upload flow, VBA cleaning toggle, sheet review UI
- `xl_parse/main.py`: parameter controls, candidate visualization
- `xl_kg/main.py`: **primary template** — executor, polling, sidebar config build, tabs, decision log
- `xl_image/main.py`: full pipeline orchestration, results browsing

## Known Disadvantages & Mitigations

### 1. xl_parse import refactor is the highest execution risk
Many files (9+), each with 10+ bare imports. Easy to miss one and get a runtime `ImportError` that only surfaces when that code path runs.

**Mitigation:** After Phase 2, immediately run a dedicated import smoke test: `python -c "from xl_parse.pipeline import parse_workbook"` and grep every `.py` file under `xl_parse/` for any remaining bare `from parse_tools` or `from block_generation`-style imports. Add a CI-style check script (`tests/test_imports.py`) that imports every public module.

### 2. xl_kg → xl_table rename touches many lines; bad replace breaks runtime subtly
A naive find-replace could mangle string literals, logger names, or comments in ways that don't cause `ImportError` but produce wrong log output, broken decision trails, or misnamed artifacts.

**Mitigation:** Do the rename in two passes: (a) imports only (`from xl_kg.` → `from xl_table.`), (b) string literals/comments/logger names separately with manual review. After both passes, grep for any remaining `xl_kg` in `.py` files — zero hits required. Add a test assertion: `assert "xl_kg" not in open(f).read()` for every `.py` under `xl_table/`.

### 3. Two YAML files + existing dataclasses can drift
`config/stages.yaml` and `config/general.yaml` define defaults, but each stage also has a Python dataclass with its own defaults. Until migration is complete, duplicated defaults can silently diverge.

**Mitigation:** The Python dataclass constructors must NOT define default values for any field that is in `stages.yaml`. Instead, `core/config.py` loads YAML first, then constructs the dataclass from the loaded dict. If a YAML key is missing, the loader raises an error (not a silent Python default). This enforces YAML as the single source of truth from day one. Document this contract in `docs/architecture.md` under "Configuration Authority."

### 4. Large Streamlit orchestrator risks bloat
Mixing four legacy UIs into one `app.py` can easily become a monolithic file with business logic leaking in, especially under time pressure.

**Mitigation:** Structure `apps/orchestrator/` as multiple files from the start: `app.py` (top-level router + tabs), `ui_init.py`, `ui_parse.py`, `ui_table.py`, `ui_image.py` (one per stage, each under 200 lines). Each UI file imports only its stage's public entry point and `core.paths`/`core.config`. Enforce a rule: no `openpyxl`, `numpy`, or stage-internal imports in any `apps/` file.

### 5. ThreadPoolExecutor + Streamlit adds complexity (session state bugs, rerun loops)
The xl_kg/main.py polling pattern (`future.done()` + `time.sleep(1)` + `st.rerun()`) works but is fragile — double-submits, stale session state, and rerun storms are common Streamlit pitfalls.

**Mitigation:** Follow the exact xl_kg/main.py pattern (proven working): one future per stage stored in `st.session_state`, guard submit button with `if not st.session_state.get("running")`, clear state keys on completion. Add a visible "Cancel" button that calls `future.cancel()`. Document the pattern in `docs/architecture.md` so future maintainers don't reinvent it.

### 6. No changes to xlgen_v2 means no shared regression harness
Validation is manual or new tests only in v3. There's no way to run both v2 and v3 on the same workbook and diff outputs automatically.

**Mitigation:** Create `tests/test_regression.py` in xlgen_v3 that (a) runs a known workbook through `run_pipeline.py`, (b) compares key artifact shapes (row counts in `final_candidates.jsonl`, number of `decisions.jsonl` entries) against expected baselines stored in `tests/fixtures/baselines/`. This is not a full regression suite but catches gross breakage. Document in ASSUMPTIONS.md that full v2-vs-v3 parity testing is deferred.

### 7. Phases 1–4 in parallel increases integration risk
If two stages are migrated concurrently and both touch `core/config.py` or `core/paths.py` contracts, they can diverge.

**Mitigation:** Phase 0 must fully lock down `core/paths.py` and `core/config.py` interfaces before any stage migration begins. Phases 1–4 consume these interfaces but do not modify them. If a stage migration discovers a missing `core/` function, it is added to a documented backlog and implemented before Phase 5 (CLI scripts), not ad-hoc during parallel work.

### 8. "Document gaps" leaves known holes open
Features like `coverage_report.json` in xl_parse are marked "document as deferred" — this is honest but means the v3 artifact contract is incomplete on day one.

**Mitigation:** Every deferred feature gets a tracked entry in ASSUMPTIONS.md with: (a) what it is, (b) why it's deferred, (c) which stage owns it, (d) the specific function/file where it should be added. This turns vague "document the gap" into an actionable backlog. Priority: features that affect downstream consumers (xl_table reading xl_parse output) are escalated; purely informational outputs (coverage reports) can wait.

### 9. Smoke test with "minimal fixture or document gap" may leave real-workbook paths unverified
A synthetic 2-sheet fixture exercises the happy path but won't catch issues with merged cells, VBA shapes, multi-table blocks, or complex grammar cuts.

**Mitigation:** The minimal fixture is the import/path smoke test only. For real validation, the plan requires running at least one actual workbook from `xlgen_v2/inputs/Example of simple BIM.xlsm` through the full pipeline. If that file is unavailable at migration time, document it as a blocking validation gap in ASSUMPTIONS.md (not a "nice to have"). The first real-workbook run after migration is a gate before declaring v3 ready.

### 10. YAML edits in Streamlit: session-only vs write-through
The plan (Phase 6) says this is an implementation choice. Leaving it unspecified risks inconsistent behavior.

**Decision:** Default to **session-only overrides** — the UI patches the loaded config in memory for the current run but does NOT write back to `config/stages.yaml` or `config/general.yaml`. Rationale: write-through from a UI is dangerous (concurrent users, partial writes, git-unfriendly diffs). Power users who want persistent changes edit YAML directly. Document this in README.md under "Configuration."
