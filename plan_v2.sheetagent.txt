1. ARCHITECTURE OVERVIEW
================================================================================

V2 replaces the sequential, deterministic-first pipeline with a parallel,
agent-based, LLM-first architecture organized into four components that
communicate through shared mutable state.

COMPONENTS
----------

  1. GrammarWorkbookAgent   (blocking, runs first)
     Selects sample tables, calls LLM to identify structural roles
     (title / column-headers / row-names), captures associated formatting,
     and builds a mutable grammar profile.

  2. TableAgent              (parallel, one per table)
     LLM-first structural reading of each table, with grammar-assisted
     shortcutting and LLM-controlled splits for large tables. Falls back
     to deterministic tools when LLM cannot decide, and escalates to
     the SheetCoordinator when all methods fail.

  3. SheetCoordinator        (per sheet, after all table agents for that sheet)
     Resolves escalated decisions (missing title, ambiguous headers,
     ambiguous row names) using sheet-level consistency and scoring signals.
     Runs section detection and tree assembly.

  4. AssemblyLayer           (sequential, runs last)
     Builds trees, relationship graphs, and writes all output files in the
     same formats as V1. Reuses existing assembly/ code.

SHARED MUTABLE STATE
--------------------

  GrammarProfile    Thread-safe (threading.Lock). Starts with patterns
                    learned by GrammarWorkbookAgent. Updated by TableAgents
                    when new formatting patterns are discovered. Reads are
                    lock-free (snapshot semantics).

  AgentResultStore  Thread-safe collection of per-table results, signals,
                    and escalation requests. Each table writes to its own
                    slot — minimal contention.

DATA FLOW
---------

  upstream_compat.load_upstream(run_id)
          |
          v
  [GrammarWorkbookAgent]  --------- BLOCKING sequential ----------
          |
          v
     GrammarProfile (mutable, thread-safe)
          |
          v
  [TableAgent per table]  --------- PARALLEL (ThreadPoolExecutor) -
     Each:
       grammar pre-check -> LLM structure read -> fallback tools
       -> escalation -> grammar update -> split decision -> interpretation
          |
          v
     AgentResultStore (enriched tables + signals + escalations)
          |
          v
  [SheetCoordinator per sheet]  --- PARALLEL per sheet ------------
     Resolves escalations, section assignment, consistency checks
          |
          v
  [AssemblyLayer]  ---------------- SEQUENTIAL --------------------
     Tree building, relationship graphs, output writing

2. AGENT ROLES
================================================================================

2.1  GrammarWorkbookAgent
------------------------------------------------------------------------
File:      xl_sheetagent/agents/grammar_workbook_agent.py

Purpose:   Learn the workbook's formatting vocabulary from a small set of
           high-confidence tables using LLM, BEFORE any per-table processing
           begins.

Inputs:
  - upstream: UpstreamData (table_objects list from xl_table)
  - ws_by_sheet: Dict[str, openpyxl.Worksheet] (data_only=True)
  - ws_formula_by_sheet: Dict[str, openpyxl.Worksheet] (data_only=False)
  - cfg: XlSheetAgentConfig

Output:
  GrammarWorkbookResult:
    - profile: GrammarProfile
    - sample_tables_used: List[str]  (table_ids)
    - llm_calls_made: int
    - debug_events: List[Dict]

Algorithm:
  1. Score all tables by (row_count <= 12, confidence DESC, density DESC).
  2. Select top ~3 small, high-confidence tables from different sheets.
     Require n_rows >= 3 (need title + header + at least 1 body row).
     Prefer diversity: at most 2 from same sheet.
  3. For each selected table (up to 5 attempts to get 3 successes):
     a. Extract first 3 rows: values + formulas (no formatting in prompt).
     b. Send to LLM: "Identify which row is the title (if any), which
        row(s) are column headers, and which column contains row names."
     c. If LLM says "no clear title" -> try next candidate table.
     d. On success: read the FORMATTING of identified cells via openpyxl:
        - Title row: font_name, font_size, is_bold, fill_color, text_color,
          whether there is an empty row above the table.
        - Column header row(s): font_name, is_bold, fill_color, text_color.
        - Row-name column: font_name, is_bold, fill_color, text_color.
  4. Aggregate formatting across 2-3 successful tables into GrammarProfile.
  5. Save profile; return for use by TableAgents.

Failure mode: If fewer than 2 tables succeed, start with an empty
GrammarProfile. All tables will use the LLM-first path (no grammar
shortcutting).


2.2  TableAgent
------------------------------------------------------------------------
File:      xl_sheetagent/agents/table_agent.py

Purpose:   LLM-first structural reading of a single table, with
           grammar-assisted shortcutting, fallback tools, escalation,
           and LLM-controlled splits.

Inputs:
  - table_view: TableObjectView (from upstream_compat)
  - upstream: UpstreamData
  - ws (data_only worksheet), ws_formula (formula worksheet)
  - grammar: GrammarProfile (shared, mutable)
  - cfg: XlSheetAgentConfig
  - recorder: ToolCallRecorder
  - trace: TraceAccumulator

Output:
  TableAgentResult:
    - enriched_table: EnrichedTableObject
    - signals: List[TableSignal]
    - escalations: List[EscalationRequest]
    - grammar_updates: List[GrammarObservation]
    - debug_events: List[Dict]

Algorithm:   (See Section 5 for full workflow detail)

  Step 0: Content bbox + context block routing (FIRST — returns early
          if context block, skipping all subsequent steps)
  Step A: Grammar pre-check
  Step B: LLM structure read (if grammar did not match)
  Step C: Fallback tools (if LLM returned "none" for any role)
  Step D: Escalation (if still unresolved)
  Step E: Grammar update (if LLM found new pattern)
  Step F: Split decision (for tables with >10 rows)
  Step G: LLM interpretation (summary, category, entities, embedding)


2.3  SheetCoordinator
------------------------------------------------------------------------
File:      xl_sheetagent/agents/sheet_coordinator_agent.py

Purpose:   Resolve escalated table-level decisions using sheet-level
           consistency and optional batch LLM reasoning. Act as
           escalation and resolution logic, not duplication of table
           agent work. May issue ONE optional LLM call per sheet to
           resolve multiple escalations at once (batch reasoning).

Inputs:
  - sheet_name: str
  - table_results: List[TableAgentResult]
  - upstream: UpstreamData
  - ws_by_sheet: Dict[str, Worksheet]
  - grammar: GrammarProfile
  - cfg: XlSheetAgentConfig

Output:
  Tuple of:
    - List[EnrichedTableObject]  (resolved)
    - List[TableSignal]
    - SheetObjectTree
    - RelationshipGraph
    - Dict  (debug events)

Algorithm:   (See Section 6 for full workflow detail)


2.4  AssemblyLayer
------------------------------------------------------------------------
Files:     xl_sheetagent/assembly/exporter.py         (modified)
           xl_sheetagent/assembly/sheet_assembler.py   (extended for rejected block nodes)
           xl_sheetagent/assembly/relationship_builder.py (extended for belongs_to/labels edges)
           xl_sheetagent/assembly/tree_renderer.py     (unchanged)

Purpose:   Build trees, relationship graphs, write all outputs.
           Reuses existing assembly code with minimal changes to handle
           new V2 grammar profile serialization and manifest fields.

SEQUENCING CONSTRAINTS:
  - Step 4 (grammar) MUST complete before Step 5 begins.
  - Step 5c (coordinator) MUST wait for all table agents on that sheet.
  - Step 7-8 (assembly/export) MUST wait for all sheets to complete.
  - Grammar updates (Step 5a) can happen during table agent execution.

4. GRAMMAR WORKBOOK GENERATION FLOW
================================================================================

4.1  SAMPLE SELECTION
---------------------

  def _select_grammar_samples(upstream, max_tables=5, prefer_max_rows=12):
      """Select small, high-confidence tables for grammar learning."""
      candidates = [
          tv for tv in upstream.table_objects
          if tv.n_rows <= prefer_max_rows
          and tv.n_rows >= 3
          and tv.density >= 0.3
      ]
      candidates.sort(key=lambda tv: (-tv.confidence, tv.n_rows))
      # Diversity: at most 2 from same sheet
      selected, sheet_counts = [], {}
      for tv in candidates:
          if sheet_counts.get(tv.sheet_name, 0) >= 2:
              continue
          selected.append(tv)
          sheet_counts[tv.sheet_name] = sheet_counts.get(tv.sheet_name, 0) + 1
          if len(selected) >= max_tables:
              break
      return selected

Config keys:
  grammar_sample_max_rows: 12      # Max rows for grammar sample tables
  grammar_sample_count: 3          # Target number of successful samples
  grammar_sample_attempts: 5       # Max tables to attempt before giving up


4.2  LLM CALL FOR STRUCTURE IDENTIFICATION
------------------------------------------

System prompt:
  "You are a spreadsheet analyst. Given the first rows of a table
   (cell values and formulas), identify the structural roles:
   1. Which row (if any) is the table title? (0-indexed row number
      relative to the table, or "none")
   2. Which row(s) are column headers? (list of 0-indexed row numbers,
      or "none")
   3. Which column (if any) contains row names/labels? (0-indexed
      column number, or "none")

   Respond ONLY with JSON:
   {"title_row": 0, "header_rows": [1], "row_name_column": 0}
   Use "none" for any role that is not present."

User prompt:
  "Table from sheet '{sheet_name}', range {bbox_excel}:
   Row 0: [cell1_value (=formula1), cell2_value, ...]
   Row 1: [cell1_value (=formula2), cell2_value, ...]
   Row 2: [cell1_value, cell2_value (=formula3), ...]"

  Values and formulas included. Formatting NOT included.

Retry logic:
  If LLM says title_row="none", skip this table and try the next
  candidate. If all header_rows="none" AND row_name_column="none",
  also skip (the table is too ambiguous to learn from).


4.3  FORMATTING CAPTURE
------------------------

After the LLM identifies roles for a successful table, read formatting
from the openpyxl data_only=True workbook (which preserves formatting):

  @dataclass
  class RoleFormatting:
      role: str              # "title" | "column_header" | "row_name"
      font_name: str | None
      font_size: float | None
      is_bold: bool
      fill_color: str | None  # hex RGB e.g. "FF0000"
      text_color: str | None  # hex RGB
      has_empty_row_above: bool  # for title role only

For each role the LLM identified:
  - Title: read formatting of all cells in the title row.
  - Column headers: read formatting of all cells in header rows.
  - Row names: read formatting of all cells in the row-name column.

Take the MODAL (most common) formatting across cells in that role
to avoid single-cell anomalies.

The profile aggregates formatting from 2-3 grammar workbook tables.
Confidence starts at 0.60 with 2 samples, rises to 0.80 with 3+.
Each subsequent TableAgent observation that confirms a pattern
increases confidence toward 0.95.

FROZEN-ON-DISK vs RUNTIME-ONLY (GrammarProfile export contract)
-----------------------------------------------------------------
  V1's GrammarSnapshot was frozen=True after Phase 0 — immutable
  once written. V2's GrammarProfile is mutable at runtime (table
  agents add observations throughout the run). This is a real
  semantic shift. The export contract is:

  FROZEN ON DISK (written to grammar_snapshot.json at run end):
    - All patterns that were confirmed by grammar workbook agent
      (source="grammar_workbook").
    - All patterns that were confirmed by >= 2 table agent
      observations (source="table_agent", status="confirmed").
    - Final confidence scores (as of run end).
    - frozen=True in the output (snapshot is immutable on disk).
    - Serialized via to_snapshot_dict(), backward compatible
      with V1 GrammarSnapshot JSON schema.

  RUNTIME-ONLY (NOT written to grammar_snapshot.json):
    - Patterns with status="observed" (only 1 observation, not
      yet promoted to confirmed).
    - The threading.Lock and internal mutation history.
    - The n_observations counter and intermediate confidence values.

  EVOLUTION LOG (written to debug/grammar_profile_evolution.jsonl):
    - Every add_observation() call is logged with timestamp, table_id,
      sheet_name, pattern delta, and running pattern count.
    - This is a debug artifact for auditing how grammar evolved
      during the run. Not loaded by the Streamlit viewer.

  This ensures grammar_snapshot.json is a stable, deterministic
  artifact that downstream consumers can rely on, while the runtime
  GrammarProfile is free to evolve during processing.

5. PER-TABLE AGENT WORKFLOW
================================================================================

For every table in upstream.table_objects, a TableAgent executes:

STEP 0 — CONTENT BBOX + CONTEXT BLOCK ROUTING (runs first)
-------------------------------------------------------------
  This step MUST run before any other step, matching V1's execution
  order (table_enricher.py runs check_context_block immediately after
  compute_content_bbox, and returns early before boundaries/splits/
  headers).

  1. Compute content_bbox via step0_prefilter.compute_content_bbox().
  2. Check context block routing:
     - If table n_rows <= cfg.context_block_max_rows
       AND formula_ratio <= cfg.context_block_formula_ceil
     - Route as context_block: is_context_block=True
     - RETURN EARLY — skip Steps A through H entirely.
  3. Otherwise, proceed to Step A.


STEP A — GRAMMAR PRE-CHECK
---------------------------
  1. Read formatting of the first 3 rows of the table via openpyxl.
  2. Compare against grammar.matches_title(), grammar.matches_header(),
     grammar.matches_row_name().
  3. If ALL THREE match with confidence >= cfg.grammar_match_threshold
     (default 0.75):
     - Assign title/headers/row_names from formatting positions.
     - Record structure_method="grammar_match" in step_log.
     - Skip Step B (no LLM call).
  4. Otherwise, proceed to Step B.

  This optimization means LLM call count DECREASES as grammar learns.
  For a 200-table workbook, the first 3-5 tables use LLM; the rest
  should mostly be grammar-matched.


STEP B — LLM STRUCTURE READ
----------------------------
  1. Build payload: first 3 rows with values + formulas (no formatting).
     Use payload_builder.build_structure_identification_payload().
  2. Send to LLM with structure-identification prompt (same as grammar
     workbook but applied to this table).
  3. Parse JSON: {title_row, header_rows, row_name_column}.
  4. If LLM returns valid assignments: apply them.
     Record structure_method="llm_structure" in step_log.
  5. If LLM returns "none" for any role: proceed to Step C for that role.


STEP C — FALLBACK TOOLS
------------------------
  Activated only for roles where LLM returned "none" or failed.

  Title fallback:
    1. Scan rows above the table (up to cfg.title_shape_proximity_max
       rows, default 2) for non-empty text that is bold or merged.
    2. Check shapes_manifest for shapes anchored near the table top.
    3. Use V1's title_attachment_score() for spatial scoring.
    4. If found: assign title, record title_source="above_bbox" or "shape".

  Header fallback:
    1. Use upstream header_row_indices if header_confidence >=
       cfg.tier_a_sufficient (default 0.80).
    2. Check rejected blocks overlapping the bbox interior.
    3. If found: assign column_headers from those rows.

  Row-name fallback:
    1. Use V1's first-nonempty-column scan (deterministic):
       scan body columns left-to-right, pick first where >= 1 cell
       is non-empty.
    2. If found: assign row_headers from that column.


STEP D — ESCALATION
--------------------
  For any role STILL unresolved after Steps B-C:

  @dataclass
  class EscalationRequest:
      table_id: str
      sheet_name: str
      role: str               # "title" | "column_headers" | "row_names"
      attempted_methods: List[str]   # e.g. ["llm_structure", "above_bbox"]
      context: Dict[str, Any]        # bbox, nearby tables, etc.

  The SheetCoordinator will receive this and attempt resolution using
  sheet-level context (see Section 6).


STEP E — GRAMMAR UPDATE
------------------------
  If the LLM provided a definitive answer in Step B AND this table's
  formatting differs from existing grammar patterns:

  @dataclass
  class GrammarObservation:
      table_id: str
      sheet_name: str
      title_formatting: RoleFormatting | None
      header_formatting: RoleFormatting | None
      row_name_formatting: RoleFormatting | None

  The orchestrator merges this into GrammarProfile under lock.
  This means later tables on OTHER sheets (processed in parallel)
  can benefit from patterns discovered on earlier-processed sheets.


STEP F — SPLIT DECISION (tables with n_rows > split_consideration_min_rows)
----------------------------------------------------------------------------
  See Section 7 for full workflow.

  Only tables with more than cfg.split_consideration_min_rows (default 10)
  are considered for splitting. The decision is made entirely by LLM
  based on cut_scores and xl_table decision context.


  (Step G removed — context block routing moved to Step 0 above,
   matching V1's execution order where it runs first and returns
   early before any enrichment steps.)


STEP G — LLM INTERPRETATION
----------------------------
  After structure is resolved (title, headers, row_names assigned):

  1. Build interpretation payload via payload_builder:
     - If table has authoritative partitions: build per-partition payloads.
     - Otherwise: build whole-table payload.
  2. Call LLM with interpretation prompt:
     System: "You are a financial spreadsheet analyst specialising in
              health economics and outcomes research (HEOR) models..."
     (Same system prompt as V1's step4_interpretation.)
  3. Parse JSON: {summary, table_category, key_entities,
     embedding_description, ontology_hint}.
  4. Apply to enriched_table: llm_summary, llm_table_category,
     rag_fields, ontology_hint.
     ontology_hint is a stable, enumerable label derived from
     table_category + LLM context. See Section 13.4.

  V1's deterministic category inference (step 9 in table_enricher)
  is retained as a fallback when LLM is unavailable or returns
  invalid category.

6. SHEET COORDINATOR WORKFLOW
================================================================================

The SheetCoordinator runs ONCE PER SHEET after all TableAgents for that
sheet have completed.

6.1  SIGNAL COLLECTION
-----------------------
  Collect from all TableAgentResults on this sheet:
    - EscalationRequest objects (unresolved title/headers/row_names)
    - TableSignal objects (orphan_rows, header_unresolved, shared_note)

6.2  TITLE RESOLUTION
----------------------
  For each escalation with role="title":
    1. Search context blocks and rejected blocks near the table for
       potential title candidates. Use V1's title_attachment_score()
       for spatial scoring.
    2. Search orphan rows that may have been detached from a table above.
    3. If a candidate is found with score >= cfg.tier_b_accept:
       assign title, record resolution_method="coordinator_spatial".
    4. If no candidate found:
       assign title=None, record title_source="unresolved".

6.3  HEADER RESOLUTION
-----------------------
  For each escalation with role="column_headers":
    1. Find the nearest RESOLVED table on the same sheet with high
       column overlap (same column range ± 1 column).
    2. Use V1's header_inheritance_score() to evaluate.
    3. If inheritance score >= cfg.header_unresolved_floor:
       assign column_headers from the donor table.
       Record resolution_method="coordinator_inheritance".
    4. If no suitable donor found:
       assign column_headers=[], record as "unresolved".

6.4  ROW-NAME RESOLUTION
--------------------------
  For each escalation with role="row_names":
    1. Check if adjacent tables in the same section have a consistent
       row-name column index.
    2. If consistent: inherit the pattern.
    3. If not: assign row_headers=[], record as "unresolved".

6.5  SECTION DETECTION
-----------------------
  Retain V1's section_detector.py logic entirely:
    - Detect section bands from rejected blocks with strong formatting
      (fill + bold, fill + large font, bold + large font).
    - Detect from workbook merged cells.
    - Return List[SectionBand] per sheet.

6.6  SECTION ASSIGNMENT
------------------------
  Assign each table to a section band using V1's
  section_ownership_score():
    - Spatial containment scoring.
    - Emit section_ambiguity signals if two bands compete.

6.7  OPTIONAL SHEET-LEVEL BATCH LLM CALL
-----------------------------------------
  When the coordinator has >= 2 unresolved escalations after
  deterministic resolution (6.2-6.4), it MAY issue a single LLM
  call per sheet to batch-resolve remaining ambiguities.

  Purpose: Replace many per-table LLM calls with one sheet-level
  reasoning call. Especially effective for header style clashes,
  repeated row-name columns, or a stack of tables sharing one title.

  System prompt:
    "You are a spreadsheet analyst. The following tables on sheet
     '{sheet_name}' have unresolved structural roles. Using sheet-level
     consistency, resolve each. Respond with JSON:
     {"resolutions": [
       {"table_id": "...", "role": "title", "value": "...",
        "reasoning": "..."},
       ...
     ]}"

  User prompt includes:
    - Per-table: bbox, resolved roles, unresolved roles, nearby context.
    - Per-table: rejected blocks in vicinity (promoted to structured
      neighbor objects, see Section 13.1).
    - Sheet-level grammar observations.

  Contract (what the sheet LLM may override):
    - Unresolved roles (title/headers/row_names where confidence < 0.60).
    - Category reclassification when table agents disagree.
  What is FROZEN (sheet LLM may NOT override):
    - xl_table bbox coordinates.
    - Split decisions already confirmed by the split agent.
    - Grammar workbook patterns (read-only during coordination).

  Idempotency: LLM temperature=0. Deterministic ordering of tables in
  the prompt (sorted by r_top, c_left). Audit trail records full prompt
  and response.


6.8  TREE ASSEMBLY
-------------------
  Reuse existing sheet_assembler.build_tree() and
  relationship_builder.build_relationships() with extensions for
  rejected block nodes (see Section 13.1).

  Input: enriched tables (with resolved structures) + section bands
         + promoted rejected blocks.
  Output: SheetObjectTree, RelationshipGraph.


================================================================================
7. SPLIT-DECISION WORKFLOW FOR LARGE TABLES
================================================================================

This section replaces V1's multi-heuristic split detection
(step2_splits.py) for tables that exceed the size threshold.

7.1  TRIGGERING CONDITION
--------------------------
  A table is considered for splitting when:
    n_rows > cfg.split_consideration_min_rows (default: 10)

  Tables at or below 10 rows are never split.


7.2  CUT LOADING
-----------------
  Gather split candidates from two sources:

  Source A — cut_scores.jsonl (from xl_parse):
    Filter entries where:
      - sheet_name matches this table
      - abs_row = entry.block_r1 + entry.index is within
        [table.r_top, table.r_bot]
      - combined_score > 0.3 (minimum signal threshold)
    Extract: abs_row, combined_score, separator_score,
             header_restart_score, changepoint_score

  Source B — decisions.jsonl (from xl_table):
    Filter split_attempt events associated with this leaf table.

    NOTE: xl_table's split_lineage contains "row:{abs_split}" strings,
    NOT candidate_id ancestry. You cannot filter by
    "candidate_id in split_lineage". Instead, match via:
      1. Walk parent_table_id chain upward from this leaf table to
         find all ancestor candidate_ids.
      2. Filter decisions.jsonl for entries where:
         - entry.sheet == this table's sheet_name
           (decisions.jsonl uses the key "sheet", not "sheet_name")
         - entry.candidate_id matches any ancestor candidate_id, OR
         - entry.bbox_excel overlaps this table's bbox (fallback for
           sub-split tables whose candidate_id was reassigned)
      3. Include both ACCEPTED and REJECTED attempts (V2 re-evaluates
         all candidates with LLM).
    Extract: split_row_abs, signal_source, decision, reason

  Deduplicate by abs_row. Combine scores from both sources.

  TOP-K FILTERING:
    After gathering all candidates, apply:
      1. Min score floor: discard candidates with combined_score <
         cfg.split_min_score_floor (default: 0.3).
      2. Structural signal gate: require at least ONE structural signal
         (separator_score > 0 OR header_restart_score > 0 OR an xl_table
         split_attempt exists) before a row enters the candidate set.
         Rows with only changepoint signal are dropped.
      3. Top-K cap: keep at most cfg.split_top_k (default: 5) candidates
         ranked by combined_score DESC.
      4. Dedup by proximity: if two candidates are within 2 rows of each
         other, keep only the higher-scored one.

    This reduces prompt noise, limits LLM cost per table, and avoids
    sending weak cuts that only add confusion.

  Sort final candidates by abs_row ascending.

  Config keys:
    split_min_score_floor: 0.3
    split_top_k: 5
    split_proximity_dedup: 2


7.3  CONTEXT EXTRACTION
------------------------
  For each candidate cut at row r_cut (0-indexed):

    NOTE ON INDEXING: All bbox coordinates in this pipeline are
    0-indexed inclusive. openpyxl uses 1-based row and column
    indices. Existing codebase helpers (step0_prefilter,
    step3_headers, section_detector) consistently convert via
    row=r + 1, column=c + 1. The split_agent MUST follow the
    same convention. Do NOT call ws.cell() with 0-based coords.

    # Convert 0-indexed r_cut to openpyxl 1-based
    row_above = [ws.cell(row=r_cut + 1, column=c + 1).value
                 for c in range(c_left, c_right + 1)]
    row_below = [ws.cell(row=r_cut + 2 + 1, column=c + 1).value
                 for c in range(c_left, c_right + 1)]

    # Same for formula workbook
    formula_above = [ws_formula.cell(row=r_cut + 1, column=c + 1).value
                     for c in range(c_left, c_right + 1)]
    formula_below = [ws_formula.cell(row=r_cut + 2 + 1, column=c + 1).value
                     for c in range(c_left, c_right + 1)]

    (Where r_cut is the 0-indexed row of the cut, r_cut + 1 is the
     row below it in 0-indexed terms, and +1 converts to openpyxl's
     1-based API. Use the existing helper pattern from step0 / step3.)

  Include upstream context:
    - combined_score from cut_scores
    - xl_table decision (if any) and reason
    - Whether the row is empty or partially empty


7.4  LLM DECISION
-------------------
  Single LLM call per table with ALL candidates bundled:

  System prompt:
    "You are a spreadsheet analyst. A large table has been extracted
     from an Excel workbook. For each proposed split boundary below,
     decide whether the table should be split at that row. A split is
     valid if there is a clear structural break: a new section header,
     a new set of column headers restarting, a visible topic change,
     or a significant empty/separator row.

     Respond ONLY with JSON:
     {"splits": [
       {"row": <abs_row>, "should_split": true, "reason": "..."},
       {"row": <abs_row>, "should_split": false, "reason": "..."}
     ]}"

  User prompt:
    "Table: sheet '{sheet_name}', range {bbox_excel}, {n_rows} rows.

     Candidate 1 (row {abs_row}, upstream_score={combined_score}):
       Row above: [val1, val2, val3, ...]
       Row below: [val1, val2, val3, ...]
       xl_table decision: {ACCEPTED|REJECTED}, reason: {reason}

     Candidate 2 (row {abs_row}, upstream_score={combined_score}):
       ..."


7.5  APPLICATION
-----------------
  For each confirmed split (should_split=true):
    Create SemanticPartition:
      partition_type = "v2_llm_split"
      authoritative = True
      sub_bbox = computed from split boundaries
      confidence = 0.85  (LLM-confirmed)
      evidence = {"source": "v2_llm_split",
                  "reason": <LLM reason>,
                  "upstream_score": <combined_score>}

  Splits are applied as partitions within the original table (same
  as V1's SemanticPartition model), not as new top-level tables.

  If LLM rejects ALL candidates: no splitting occurs. The table
  remains whole.

8. PARALLELIZATION STRATEGY
================================================================================

8.1  THREAD MODEL
------------------

  Primary:  ThreadPoolExecutor (not asyncio)
  Reason:   openpyxl is not async. LLM calls are I/O-bound but the
            OpenAI Python SDK supports threading natively. asyncio
            would require aiohttp and async openpyxl (neither exists).

  Workers:  cfg.max_parallel_sheets (default: min(4, len(sheets)))


8.2  SHEET-LEVEL PARALLELISM
------------------------------

  Each sheet is submitted as a single task to the ThreadPoolExecutor:

    def _process_sheet(sheet_name, tables, upstream, grammar, cfg, ...):
        # Open per-thread workbook handles
        wb_local = openpyxl.load_workbook(path, data_only=True, read_only=True)
        wb_formula_local = openpyxl.load_workbook(path, data_only=False, read_only=True)
        ws = wb_local[sheet_name]
        ws_formula = wb_formula_local[sheet_name]

        # Process each table
        results = []
        for table in tables:
            result = run_table_agent(table, ..., ws, ws_formula, grammar, ...)
            results.append(result)
            # Merge grammar updates
            for obs in result.grammar_updates:
                grammar.add_observation(obs)  # Thread-safe

        # Run coordinator
        resolved = run_sheet_coordinator(sheet_name, results, ...)

        # Close per-thread handles
        wb_local.close()
        wb_formula_local.close()

        return resolved


8.3  TABLE-LEVEL PARALLELISM WITHIN A SHEET
---------------------------------------------

  Tables within a sheet are processed SEQUENTIALLY by default.
  Reason: grammar updates from earlier tables benefit later tables
  on the same sheet. Sequential processing maximizes grammar
  shortcutting within a sheet.

  Optional: tables on the same sheet CAN be parallelized if grammar
  is already high-confidence (>= 0.80). This is a future optimization.


8.4  WHAT IS SEQUENTIAL (NOT PARALLELIZED)
--------------------------------------------

  1. load_upstream()            — reads files, must be first
  2. GrammarWorkbookAgent       — must complete before TableAgents
  3. detect_text_dominant_sheets — cheap, runs before grammar
  4. AssemblyLayer / write_outputs — must be after all processing
  5. Manifest building          — after all processing


8.5  THREAD SAFETY DETAILS
----------------------------

  GrammarProfile._lock:
    - add_observation() acquires lock.
    - matches_*() reads snapshot of list (no lock needed;
      list.append is atomic in CPython, and reads of a slightly
      stale list are acceptable — worst case, a table misses
      one pattern and falls through to LLM).

  AgentResultStore._lock:
    - Thread-safe append for per-table results.
    - Each table writes to its own slot (table_id key).

  TraceAccumulator / ToolCallRecorder:
    - Add threading.Lock to __init__.
    - Each record() / finalize_table() call acquires lock.

  openpyxl:
    - NOT thread-safe. Each thread opens its own workbook handle
      in read_only mode. This is safe and cheap (read-only mode
      uses iterators, not full cell caching).

  OpenAI client:
    - Thread-safe per documentation. Share one client instance
      across all threads (created at startup, passed to all agents).
    - Replaces V1's per-call client creation.

  Python logging:
    - Thread-safe by default.


8.6  DETERMINISTIC OUTPUT ORDERING
------------------------------------

  To ensure stable, reproducible outputs regardless of thread
  scheduling order:
    - Sort enriched_tables by (sheet_name, r_top, c_left) before export.
    - Sort signals by (source_table_id).
    - Sort trees_by_sheet by sheet_name.
    - Sort debug_events by (table_id, event_ts).

================================================================================

ASSUMPTIONS
-----------

  A1. LLM AVAILABILITY
      V2 requires an LLM to function. When skip_llm_enrichment=true,
      the system falls back to V1's deterministic pipeline entirely
      (not V2 with LLM disabled). The v2_enabled flag is ignored
      when skip_llm_enrichment=true.

  A2. OPENPYXL READ-ONLY THREADING
      Opening multiple read-only openpyxl workbook handles to the
      same file is safe on Windows. This is documented behavior
      (read-only mode uses file iterators, not exclusive locks).

  A3. LLM CONSISTENCY
      The LLM returns consistent structural identifications for
      tables with similar formatting. The grammar profile's voting
      logic handles occasional disagreements by requiring >= 2 of 3
      formatting attributes to match.

  A4. TOKEN BUDGET
      Sending 3 rows of a table fits within LLM token limits.
      For very wide tables (100+ columns), the payload builder must
      truncate to the first 20 columns with a note "[{n} more cols]".

  A5. OPENAI CLIENT THREAD SAFETY
      The OpenAI Python client is thread-safe for concurrent
      chat.completions.create() calls, as documented.


RISKS
-----

  R1. LLM COST
      V2 makes ~2-3 LLM calls per table (structure read + possible
      split + interpretation). For a 200-table workbook: 400-600 calls.

      Mitigations:
        - Grammar shortcutting: after 5-10 tables, most should be
          grammar-matched (0 LLM calls).
        - Batch grammar workbook: 3 tables in potentially 1-2 calls.
        - Use cheaper models for structure ID (gpt-3.5-turbo) and
          reserve gpt-4 for interpretation.
        - Track LLM cost in run_manifest for monitoring.

  R2. NON-DETERMINISM FROM PARALLELISM
      If grammar evolves differently depending on thread scheduling
      order, outputs may differ between runs.

      Mitigations:
        - Grammar workbook (blocking phase) provides a stable
          baseline before parallel processing begins.
        - Grammar updates are append-only (never remove patterns).
        - Tables within a sheet are processed sequentially.
        - Final grammar state is independent of update order
          (pattern matching uses attribute comparison, not ordering).

  R3. THREAD SAFETY OF GRAMMAR PROFILE
      Lock contention could bottleneck parallel execution if many
      threads try to update grammar simultaneously.

      Mitigation:
        - Updates are rare (only when a genuinely NEW formatting
          pattern is discovered; most tables confirm existing patterns).
        - Lock is only held during append (microseconds).
        - Reads are lock-free.

  R4. WIDE TABLE TRUNCATION
      The LLM cannot see all columns of a 50-column table in 3 rows.

      Mitigation:
        - Truncate to first 20 columns in the payload.
        - Include a note: "[{n} additional columns not shown]"
        - The LLM's structural identification (title row, header rows)
          is typically evident from the first few columns.

  R5. LLM PROMPT BRITTLENESS
      LLM may not always return valid JSON or may misidentify roles.

      Mitigations:
        - JSON parsing with fallback (strip code fences, retry parse).
        - Validate LLM response against expected schema.
        - Fallback chain (Steps C-D) handles LLM failures gracefully.
        - Temperature=0 for deterministic results.


OPEN QUESTIONS
--------------

  Q1. SHOULD THE GRAMMAR WORKBOOK AGENT ALSO DETECT SECTION HEADERS?

      V1 grammar detected "section_header" patterns from formatting.
      V2's grammar focuses on title / header / row-name.
      Should section headers be a fourth role learned from LLM?

      Recommendation: Yes — add a fourth role. The section_detector
      can then use LLM-learned section patterns in addition to its
      existing formatting heuristics.

  Q2. FORMULA REPRESENTATION IN LLM PROMPTS

      "Send first 3 rows: values + formulas." Should formulas be
      sent as A1-style strings (=SUM(B2:B10)) or as computed values?

      Recommendation: Send BOTH — the computed value AND the formula
      string if it exists. Format: "42.5 (=SUM(B2:B10))". This gives
      the LLM maximum context for distinguishing calculated vs input
      cells.

  Q3. SHOULD V2 STILL EMIT V1-STYLE SIGNALS?

      V1 emits orphan_rows, header_unresolved, shared_note signals.
      V2 replaces much of this with escalation requests.

      Recommendation: Yes, emit both for backward compatibility.
      Escalation requests are V2-internal; signals feed into the
      Streamlit viewer and debug explorer.

  Q4. HOW MANY THREADS PER SHEET?

      For table-level parallelism within a sheet: 1 thread (sequential)
      is recommended initially. Future optimization can add intra-sheet
      parallelism for high-confidence grammar (>= 0.80).

  Q5. SHOULD INTERPRETATION (STEP H) BE BATCHED?

      V1 runs interpretation as a separate Phase 3 after all
      enrichment. V2 runs it per-table inside the TableAgent.
      Could we batch multiple tables' interpretation prompts into
      a single LLM call to reduce cost?

      Recommendation: Start with per-table calls (simpler, easier
      to debug). Optimize to batching if LLM cost is a concern
      after initial benchmarking.

13. V2 ENHANCEMENTS (ADDENDA)
================================================================================

These five enhancements tighten the V2 design: 4 + 5 + 7 form a bundle
for "same or better quality, fewer tokens." 3 improves grounding for
titles and sections. 6 is orthogonal but cheap to add early.


13.1  REJECTED BLOCKS AS FIRST-CLASS GRAPH OBJECTS
----------------------------------------------------

Today rejected blocks are list-shaped context (upstream.rejected_blocks,
used near boundaries/titles). V2 promotes them to nodes in the
SheetObjectTree alongside tables, sections, and partitions.

This matches how analysts think: floating headers, side labels, and
"ghost" structure are real objects that affect nearby tables.

NODE SCHEMA:
  New node_type values for TreeNode:
    "rejected_block"     — a block rejected by xl_parse/xl_table
    "floating_label"     — a rejected block identified as a label
    "orphan_header"      — a rejected block identified as a header

  Additional fields on TreeNode:
    rejection_source: str | None     # "xl_parse" | "xl_table"
    rejection_reason: str | None     # "too_small" | "low_density" | etc.
    block_confidence: float          # Parse-level confidence (0-1)

EDGE TYPES:
  New relationship edges:
    "belongs_to"   — rejected block belongs to a table or section
    "labels"       — rejected block labels (serves as title for) a table
    "annotates"    — rejected block annotates a table (already exists)

QUALITY GATE:
  Not all rejected blocks should be promoted. Filter by:
    - block_confidence >= 0.3 (from rejection metadata)
    - n_cells_on >= 1 (not completely empty)
    - Spatial proximity to a table (within 5 rows above/below or
      overlapping column range)
  This prevents parse noise from polluting the graph.

TREE SCHEMA VERSIONING:
  Add "tree_schema_version": "2.0" to the SheetObjectTree root.
  Consumers that assume "tables only" check this field and handle
  new node types gracefully (skip unknown types). The Streamlit
  viewer already renders node_type as a column and will display
  new types without code changes.

USAGE IN COORDINATOR:
  The SheetCoordinator can now feed structured neighbor objects
  (not just "nearby text") into title/header resolution prompts.
  This makes the optional sheet-level LLM call (Section 6.7) more
  actionable: the prompt says "rejected block B at row 5 contains
  bold text 'Financial Summary'" rather than dumping raw JSON.


13.2  STRENGTHENED SHEET COORDINATOR (AGENTIC + OPTIONAL SHEET-LEVEL LLM)
--------------------------------------------------------------------------

The SheetCoordinator evolves from pure deterministic resolution to a
two-tier system: deterministic-first, optional batch LLM for unresolved
remainder. See Section 6.7 for the full LLM call specification.

BENEFITS:
  - Batch reasoning: resolves header style clashes, repeated row-name
    columns, and stacked-table title assignment in a single LLM call
    instead of many per-table structure calls.
  - Reduces total LLM cost: one sheet LLM call replaces N per-table
    fallback calls that the table agents would otherwise make.
  - Consistency: the LLM sees ALL unresolved tables on the sheet at
    once, so it can enforce consistent style (e.g., "all 8 tables in
    this section use column A as row names").

RISKS AND MITIGATIONS:
  - Override contract: the sheet LLM may NOT override xl_table bboxes,
    confirmed splits, or grammar workbook patterns. Only unresolved
    roles with confidence < 0.60 are eligible for override.
  - Deterministic ordering: tables presented to the LLM are sorted by
    (r_top, c_left) for reproducibility.
  - Audit: the full prompt + response is recorded in escalation_log.jsonl
    and the enriched_table.step_log with resolution_method =
    "coordinator_batch_llm".

CONFIG:
  coordinator_batch_llm_threshold: 2
    Minimum number of unresolved escalations needed to trigger the
    sheet-level LLM call. If only 1 escalation remains, deterministic
    methods are sufficient.


13.3  EXPLICIT CONFIDENCE SYSTEM (METHOD vs. CONFIDENCE SEPARATION)
--------------------------------------------------------------------

Every structural decision on an enriched table carries BOTH:
  - method: HOW the decision was made
  - confidence: HOW SURE we are about it

This separation matches the repo's existing pattern (header_confidence,
table_category_confidence) and avoids resurrecting heuristic gates as
decision-makers.

PER-ROLE CONFIDENCE RECORD:
  decision_confidence: Dict[str, MethodConfidence]

  @dataclass
  class MethodConfidence:
      method: str          # "grammar" | "llm_structure" | "fallback"
                           # | "coordinator_deterministic"
                           # | "coordinator_batch_llm" | "upstream"
      confidence: float    # 0.0-1.0
      source_table_id: str | None   # For inherited decisions
      evidence: Dict       # Method-specific evidence

  Example:
    {
      "title": {"method": "llm_structure", "confidence": 0.92,
                "source_table_id": null,
                "evidence": {"llm_raw": {"title_row": 0}}},
      "column_headers": {"method": "grammar", "confidence": 0.85,
                         "source_table_id": null,
                         "evidence": {"pattern_id": "header_bold_fill"}},
      "row_names": {"method": "coordinator_deterministic",
                    "confidence": 0.60,
                    "source_table_id": "tbl_abc123",
                    "evidence": {"inherited_from": "tbl_abc123",
                                 "column_overlap": 0.95}}
    }

ESCALATION RULE:
  The SheetCoordinator only processes escalations where:
    - confidence < cfg.coordinator_escalation_floor (default 0.60), OR
    - methods disagree (grammar says one thing, upstream says another)

  This prevents the coordinator from re-doing work that table agents
  already resolved with high confidence.

USAGE IN ASSEMBLY:
  The confidence record flows through to enriched_tables.json output.
  Downstream consumers can filter by confidence (e.g., "only trust
  titles with confidence >= 0.80").


13.4  ONTOLOGY HOOK (ontology_hint)
-------------------------------------

A stable, enumerable label on each enriched table that classifies
the table's domain role. Derived from table_category + LLM context.

PURPOSE:
  Enables RAG / Q&A pipelines to filter and route tables by domain
  meaning without parsing free-text summaries. Small surface area,
  big downstream value.

SCHEMA:
  ontology_hint: str | None

  Allowed values (HEOR domain):
    "cost"           — cost input, unit cost, resource cost
    "utility"        — utility/disutility values, QALYs
    "comparator"     — treatment comparisons, arm definitions
    "efficacy"       — clinical efficacy, hazard ratios, ORs
    "population"     — cohort definitions, baseline characteristics
    "transition"     — transition probabilities, Markov states
    "sensitivity"    — sensitivity analysis inputs/outputs
    "summary"        — model results, summary outputs
    "assumption"     — documented assumptions
    "reference"      — literature references, citations
    "metadata"       — index, table of contents, navigation
    null             — unclassifiable or not attempted

DERIVATION:
  1. Primary: LLM interpretation (Step H) returns ontology_hint
     alongside table_category. Added to the interpretation prompt.
  2. Fallback: deterministic mapping from table_category:
       "input" -> "cost" (if key_entities contains cost terms)
       "output" -> "summary"
       "reference" -> "reference"
       "note" -> "assumption"
       etc.
  3. Confidence: same as table_category_confidence.

CONFIG:
  ontology_hint_enabled: true
    When false, ontology_hint is always null (saves LLM tokens
    by not adding it to the interpretation prompt).

  Ontology mapping conflicts (e.g., HEOR "outcome" vs generic
  "result") should be documented in a mapping module:
    xl_sheetagent/tools/ontology_map.py

DOWNSTREAM COMPATIBILITY:
  The field is optional (None-able). Consumers that do not use it
  simply ignore it. No Streamlit viewer changes needed — it will
  appear in the Table Inspector's full JSON expansion.


13.5  SPLIT LOGIC: TOP-K CANDIDATE FILTERING
-----------------------------------------------

See Section 7.2 for the full specification (already integrated).

Summary of the enhancement:
  - Min score floor: combined_score >= 0.3 (configurable).
  - Structural signal gate: at least one structural signal required
    (separator_score > 0 OR header_restart_score > 0 OR xl_table
    split_attempt exists). Changepoint-only rows are dropped.
  - Top-K cap: at most 5 candidates per table (configurable).
  - Proximity dedup: within 2 rows, keep only the higher-scored.

EFFECT:
  - Reduces prompt noise for the LLM split decision call.
  - Limits LLM cost per table (fewer candidates = shorter prompt).
  - Avoids sending weak cuts that only add confusion.
  - Works synergistically with the LLM-only split design: cleaner
    input leads to better LLM decisions.

Config keys (already added to Section 9.2):
  split_min_score_floor: 0.3
  split_top_k: 5
  split_proximity_dedup: 2

     Replacement: table_agent.py Steps B-C
     Reason: V2 uses LLM-first. The 4-level cascade (upstream ->
     shapes -> rejected_blocks -> LLM fallback) is inverted: LLM
     is primary, upstream/spatial are fallbacks.

  6. steps/step4_interpretation.py — V1 Phase 3 LLM interpretation
     Replacement: folded into table_agent.py Step H
     Reason: V2 runs interpretation per-table inside the agent,
     not as a separate phase.

  7. tools/v1c_review.py — V1C confirmation payloads
     Replacement: not needed
     Reason: V2 does not use the V1C confirmation pattern
     (confirm_footnote, confirm_split, confirm_row_header).
     The LLM-first approach makes confirmations unnecessary.

DO NOT DELETE these files. Keep them for V1 fallback mode
(v2_enabled=false).
