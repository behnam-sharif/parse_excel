==================================================
GOAL OF V3A
==================================================

V3A is a simple, inspectable system.

Each table is treated as an independent agent that:
- identifies its core data region (numeric/formula-heavy)
- extracts candidate semantic pieces:
  - title
  - header row
  - row names
  - footnotes / nearby text
- decides which nearby text belongs to this table
- sends anything that does NOT belong to this table to a sheet-level container

Each sheet has a **Sheet Coordinator** that:
- ONLY collects pieces
- does NOT resolve, assign, or infer anything yet

The purpose of V3A is:
👉 make table-level behavior transparent and debuggable in Streamlit

==================================================
CORE DESIGN
==================================================

1. Table Agents
- Every table from xl_table becomes one Table Agent
- Each Table Agent works independently (within its sheet)

Each Table Agent should:
- optionally trim empty outer margins (keep original bbox)
- identify a **core data region** (numeric/formula-heavy, not only formulas)
- scan above it → title/header candidates
- scan left → row-name candidates
- scan below/right → footnote / nearby text candidates

Then:
- use LLM ONLY to decide ownership:
  - belongs to this table
  - belongs to another table
  - belongs to sheet-level context

Also:
- optionally detect if the table bbox contains more than one logical region (split)

2. Sheet Coordinator (VERY IMPORTANT)
- One per sheet
- It is ONLY a container

It should collect:
- all pieces sent from table agents
- leftover text regions on the sheet that are outside all table bboxes (from upstream)

It should NOT:
- resolve titles
- assign headers
- infer ownership
- merge anything

No intelligence yet — only storage.

3. Candidate Types (ONLY THESE 4)
- title_candidates
- header_row_candidates
- row_name_candidates
- footnote_candidates

Do not expand beyond these for V3A.

4. LLM usage (minimal and focused)
LLM should only be used for:
- ownership decision (this table vs other table vs sheet)
- optional split decision

Do NOT use LLM for:
- initial scanning
- numeric/text detection
- structural detection

5. Parallelization
- parallelize at the sheet level
- inside a sheet, table agents can run sequentially (simpler and safer for now)

==================================================
STREAMLIT VIEW (VERY IMPORTANT)
==================================================

The output must be designed for easy inspection in Streamlit.

We want to clearly see what happened.

For each sheet:
- list all tables
- list sheet coordinator

For each table, show:
- table name + coordinates (bbox)
- working/trimmed bbox
- core data region (numeric/formula chunk)
- candidate groups:
  - title
  - header row
  - row names
  - footnotes
- for each candidate:
  - text
  - location
  - decision (kept vs sent to coordinator)

Also show:
- what was sent to sheet coordinator

LLM:
- show a **simple summary of each LLM decision**
- allow expanding to see full payload and response (but not by default)

For sheet coordinator:
- show all collected pieces:
  - from tables
  - from leftover sheet regions

==================================================
IMPORTANT DESIGN PRINCIPLES
==================================================

- Reuse upstream outputs (xl_parse, xl_table). Do not recompute.
- Keep V3A simple — no grammar system, no ontology, no advanced reasoning.
- Focus on clarity and inspectability.
- Use deterministic logic first, LLM only where needed.
- Treat numeric-heavy regions as core, not only formula cells.
- Avoid over-engineering — keep modules simple and logical.
